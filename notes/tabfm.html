TabFM: in-context learning for tables

Google's tabular foundation model, from 30 June 2026: hand it your labelled rows and the rows to predict, and it answers in a forward pass, with no training on your data. What it is, how it works, where it beats gradient-boosted trees and where it doesn't.

About 12 minutes · builds on the attention and transformer notes · labelled rowsattention

In short

  1. TabFM (Google Research, blog 30 Jun 2026; paper arXiv 2609.37959) is a transformer pretrained only on synthetic tables. You give it training rows with labels and test rows without, as one input, and it predicts the test labels with frozen weights. No gradient steps on your data.
  2. That's in-context learning, the same idea as an LLM learning from examples in its prompt. It descends from TabPFN (Nature, 2025) and TabICL (ICML 2025).
  3. Architecture: each cell becomes a token; the encoder alternates attention across rows within a column and attention across features within a row; each row becomes one vector; a 24-layer predictor lets every row attend to the labelled rows only.
  4. It's invariant to row order by design, but not to column order (RoPE and column grouping); it gets close by averaging 32 column-shuffled views.
  5. On Google's own TabArena numbers it beats tuned gradient-boosted trees and AutoML. In practice, trees still win on huge, imbalanced, latency-critical problems like fraud, and the open weights are non-commercial.

01The idea: learn to learn from a table

The usual way: for each new dataset, train a model (XGBoost, say) with gradient steps. The in-context way: train one model, once, on millions of datasets, so that it learns the act of fitting. Then a new dataset is just its input.

\[ \min_\theta\ \mathbb{E}_{D \sim p(D)} \Big[ -\log q_\theta\big(y_{\text{test}} \mid x_{\text{test}},\ D_{\text{train}}\big) \Big] \]

In words: over many synthetic datasets, get better at predicting each held-out label from the labelled rows.

  • Each pretraining example is a whole dataset drawn from a prior \(p(D)\), split into training rows (with labels, in context) and test rows (labels hidden, to be predicted).
  • Minimizing this loss over many datasets makes \(q_\theta\) approximate the posterior predictive \(p(y \mid x, D_{\text{train}})\): amortized Bayesian inference. That's why it's called a prior-data fitted network (TabPFN). The model has learned what a good fit looks like for data like the prior.
  • Why the posterior predictive: each synthetic dataset is made by drawing a rule \(\phi\) from the prior, then sampling rows from it. So, given the labelled rows, a held-out label's true distribution is exactly the Bayesian posterior predictive:
    \[ p(y \mid x, D_{\text{train}}) = \int p(y \mid x, \phi)\, p(\phi \mid D_{\text{train}})\, d\phi \]
    In words: consider every rule \(\phi\) that could have generated the data, weight each by how plausible the prior made it and how well it explains the training rows, and average their predictions. Log loss is lowest when the predicted distribution equals the true one (any mismatch adds a KL-divergence penalty), so training pushes \(q_\theta\) towards it. Computing that average directly is intractable; the network learns to approximate it in one forward pass, paying the cost once in pretraining (“amortized”).
  • Why synthetic data works: the prior is built from random structural causal models (random graphs of features causing other features and the label, with noise and non-linearities), which covers the kinds of structure real tables have. Real tables that look like the prior transfer well.

In-context learning vs fine-tuning

Fine-tuning changes the weights with gradients on your data. In-context learning keeps the weights frozen and conditions on your data inside the forward pass: the “training” happens in the activations. The cost moves from training time to prediction time, and the amount of data is capped by the context size.

02How TabFM works

  • Tokens. Each cell becomes a token through 32 learned Fourier frequencies, with separate embeddings for numeric and categorical values. Training rows also get a label embedding; test rows don't. Why Fourier features: a number times one weight vector gives an embedding that changes linearly with the value, which makes sharp thresholds hard to express; sines and cosines at many frequencies let the model react to small differences in a value.
  • Column attention (across rows). For each feature, its cells attend to each other down the column, so each value is seen in the context of the column's distribution (is this income high for this dataset?), like a normalization learned on the fly. It uses 256 inducing points, which makes it linear in the number of rows, and only the labelled training rows are summarized.
    • How inducing points work: 256 learned vectors first attend to the column's labelled cells, summarizing them; then every cell attends to those 256 summaries. No step compares all rows with all rows, so the cost grows linearly with rows, and test rows can't leak into the summary.
  • Row attention (across features). Within each row, the features attend to each other, with RoPE positions, so the model learns interactions between columns. It alternates with column attention for two stages.
  • Row vectors. Eight CLS tokens per row are combined into one vector per row.
  • Predictor. A 24-layer transformer over those row vectors. A mask lets every row attend only to the labelled training rows, the in-context “training set”. Attention weights those rows by similarity and averages their label information, like a soft nearest-neighbour vote with a learned similarity. It outputs class logits (up to 10 classes) or a regression value.

TabFM's forward pass, in pseudocode (simplified)

# X_train: (N, F) with labels y_train;  X_test: (M, F) without labels
tokens = cell_embed(concat([X_train, X_test]))      # (N+M, F, d): one token per cell
tokens[:N] += label_embed(y_train)                  # only training rows carry their label
for stage in range(2):
    tokens = column_attention(tokens, context=N)    # down each column, summarizing the training rows
    tokens = row_attention(tokens)                  # across each row's features (RoPE)
rows = pool_cls(tokens)                             # (N+M, d): one vector per row
mask = attend_only_to(range(N))                     # every row sees the labelled rows, test rows not each other
y_test = head(predictor(rows, mask)[N:])            # 24 layers; predictions for the M test rows
# no gradient steps on your data; by default average 32 column-shuffled views

Why not flatten the table into one long sequence?

Attention over every cell of a \(T\)-row, \(H\)-column table costs \(O(T^2 H^2)\), and it would impose an order that doesn't exist. Attending along columns, then along rows, then between whole rows keeps the cost manageable (context up to about 16K rows) and matches the table's two axes.

03Invariance: rows yes, columns approximately

  • Rows: reordering the rows doesn't change predictions. Rows get no positional encoding, and test rows are masked from each other. That's the right property, since a table's rows are a set.
  • Columns: reordering columns does change predictions, because row attention uses RoPE and columns are grouped with nearby ones. TabFM approximates column invariance by averaging the predictions of 32 column-shuffled views by default. So the default isn't literally a single forward pass, even though the blog describes one.

Why rows come out order-free: attention with no position code is a set operation. Its weights depend only on content, so reordering the inputs just reorders the outputs, \(\text{Attn}(PX) = P\,\text{Attn}(X)\) for any reordering \(P\): each output moves with its row but doesn't change. The labelled rows enter every prediction as a set that attention sums over, and the mask means a test row's prediction depends only on its own features and the labelled rows, never on which other rows are predicted alongside it.

Why give columns a position at all: the likely reason (the argument TabICL made for its own RoPE) is that without one, two columns with similar value distributions get nearly identical embeddings, and the model can't tell them apart. A position code breaks the tie at the cost of order dependence. Grouping nearby columns has the same side effect: consecutive columns are handled together in small groups, so which features share a group depends on the column order. Averaging over random column orders then washes most of that dependence out; it's approximate, since exact invariance would need every ordering, and it doubles as an ensemble that usually improves accuracy.

04Pretraining and size

  • Data: synthetic only, “hundreds of millions” of tables generated from structural causal models, with up to 100 columns. The context grew from 2,048 to 16,384 rows during training.
  • Size: 408.7M parameters in the paper; the released checkpoint is larger, about 1.6B by its weight file.
  • Limits: classification up to 10 classes, plus regression; the library accepts up to 500 features and subsamples larger tables. Compute grows quadratically with the number of context rows, because in the predictor every row attends to every labelled row, so a GPU is expected.
  • Licence: the code is Apache-2.0, but the released weights are for non-commercial, non-production use. There's also a BigQuery preview (50 feature columns, 10 classes).

The family it belongs to

  • TabPFN v2 (Hollmann et al., Nature, Jan 2025): the prior-data fitted network that started this line; designed for up to about 10K rows and 500 features.
  • TabICL (ICML 2025) and TabICL v2 (Feb 2026): column-then-row encoders with in-context learning over rows, scaling to larger tables. TabFM is roughly a hybrid of TabPFN and TabICL.

06Interview questions

1What is TabFM, in one minute?

TabFM is a transformer from Google Research (June 2026), pretrained only on synthetic tables, that predicts labels for new rows from your labelled rows in a single forward pass, with no training on your data.

  • How it's used: pass the labelled training rows and the unlabelled test rows together as one input; the weights stay frozen. This is in-context learning, the same idea as an LLM following the examples in its prompt.
  • How it learned to do that: pretraining showed it hundreds of millions of synthetic datasets drawn from a prior, the distribution the synthetic tables come from. The prior is built from structural causal models: random graphs where features cause each other and the label. Each dataset was split into labelled rows and rows to predict, and minimizing the loss on the hidden labels taught it the act of fitting itself: approximate Bayesian prediction for data like that prior.
  • Architecture: each cell becomes a token; an encoder alternates attention down each column (each value against its column's distribution) and across each row (feature interactions); each row is pooled into one vector; a 24-layer predictor lets every row attend only to the labelled rows.
  • Where it stands: on Google's own results on TabArena, a public tabular benchmark, it beats tuned gradient-boosted trees and AutoML. Limits: a context of about 16K rows, at most 10 classes, GPU cost, and non-commercial weights.

Follow-up: it descends from TabPFN and TabICL; “foundation model” means one pretrained model reused on any table.

2Why row and column attention instead of flattening the table?

A table has two axes that mean different things, and flattening it into one long sequence is both too expensive and wrong about the structure.

\[ \begin{aligned} \text{cost of flattened attention} &= O\big((TH)^2\big) = O(T^2 H^2) \\ \text{cost of column attention} &= O(T H m) \\ \text{cost of row attention} &= O(T H^2) \\ \text{cost of the predictor} &= O(T^2) \end{aligned} \]

In words: \(T\) rows and \(H\) columns make \(TH\) cell tokens, and full attention compares every pair. Mixing along one axis at a time means no step pays for both axes squared. Here \(m\) is the number of inducing points (256).

  • Column attention lets each cell see the other values in its column, so a value is read relative to that column's distribution (is this income high for this dataset?), like a normalization learned on the fly. With inducing points, \(m\) learned vectors first summarize the column's labelled cells, then every cell reads those \(m\) summaries, so the cost is linear in rows.
  • Row attention lets a row's features see each other, which is where interactions are learned (income relative to loan size, say).
  • The predictor is where each row is compared with the labelled rows: attention weights them by similarity and averages their label information, like a soft nearest-neighbour vote with a learned similarity. It's the step that actually learns from the data.
  • No fake order: a flattened sequence imposes a reading order (row 1 cell 1, row 1 cell 2, …) that a table doesn't have.

Follow-up: it's the same factorization as axial attention in images and video.

3Is it permutation-invariant?

Over rows, yes, exactly. Over columns, no: it gets close by averaging its predictions over 32 shuffled column orders.

\[ \text{Attn}(P X) = P\, \text{Attn}(X) \quad \text{for any reordering } P \text{ of the inputs} \]

In words: attention with no position code is a set operation. Its weights depend only on content, so reordering the inputs just reorders the outputs the same way: each output moves with its row but doesn't change. A test row's prediction is therefore invariant to row order.

  • Rows: rows get no position code, and the labelled rows enter every prediction as a set that attention sums over, so their order can't matter. The mask stops test rows from seeing each other, so a test row's prediction depends only on its own features and the labelled rows, not on which other rows are predicted alongside it. That's the right property, since a table's rows are a set.
  • Columns: row attention uses RoPE, a position code by column index, so the model knows where each feature sits. Nearby columns are also grouped: consecutive columns are handled together in small groups, so which features share a group depends on the column order. Both make reordering change the output. The likely reason for a position code at all (the argument TabICL made): without one, two columns with similar value distributions get nearly identical embeddings, and the model can't tell them apart.
  • The fix: averaging over 32 random column orders washes out most of the order effect. It's approximate (exact invariance would need every ordering) and doubles as an ensemble that usually improves accuracy, at 32 times the compute. So the default isn't literally one forward pass.
4How does in-context learning differ from fine-tuning?

Fine-tuning learns from your data by changing the weights with gradient steps. In-context learning keeps the weights frozen and learns from your data inside the forward pass, by reading it as part of the input.

\[ \begin{aligned} \text{fine-tune:}\quad \theta_{t+1} &= \theta_t - \eta\, \nabla L(\theta_t;\, D_{\text{train}}) \\ \text{then:}\quad \hat y &= f_{\theta_T}(x) \\ \text{in-context:}\quad \hat y &= f_{\theta}(x,\ D_{\text{train}}) \end{aligned} \]

In words: fine-tuning takes \(T\) gradient steps on your data and stores what it learned in the weights, once; in-context learning keeps the pretrained \(\theta\), holds what it learns in the activations, and recomputes it for every prediction.

  • Cost moves to prediction time: there's no training run, but every prediction attends over the whole context, so inference is heavier and grows with the number of labelled rows. Fine-tuned models and trees pay once to train, then predict cheaply.
  • Data is capped: only what fits in the context is used, and bigger tables are subsampled. Fine-tuning can use all of it.
  • No tuning, instant updates: there are no training hyperparameters and no gradient steps that could overfit a small dataset. To update the model after drift, swap in fresh labelled rows.
  • Bounded by pretraining: the model can only do the kinds of fitting its prior taught it; fine-tuning can adapt to structure the prior never covered.

Follow-up: the two can be combined: a pretrained in-context model can be fine-tuned on a family of related tables and still be used in context afterwards.

5Why does pretraining on synthetic data work?

Because the model isn't learning facts about any real dataset. It's learning the procedure of predicting from labelled examples, and that procedure can be learned from any data whose structure resembles real tables.

\[ \begin{aligned} &\min_\theta\ \mathbb{E}_{D \sim p(D)} \big[-\log q_\theta(y \mid x, D_{\text{train}})\big] \\ \Rightarrow\quad q_\theta(y \mid x, D_{\text{train}}) &\approx p(y \mid x, D_{\text{train}}) \\ p(y \mid x, D_{\text{train}}) &= \int p(y \mid x, \phi)\, p(\phi \mid D_{\text{train}})\, d\phi \end{aligned} \]

In words: each synthetic dataset is made by drawing a rule \(\phi\) from the prior, then sampling rows from it. So, given the labelled rows, a held-out label's true distribution is exactly the Bayes average on the last line: every possible rule, weighted by how plausible the prior made it and how well it explains the training rows. Log loss is lowest when the prediction matches the true distribution (any mismatch adds a KL-divergence penalty), so training pushes \(q_\theta\) towards it.

  • Amortized inference: exact Bayesian prediction over all those rules is intractable. The network learns to approximate it in one forward pass; the expensive part was paid once, in pretraining.
  • Why this prior: random structural causal models (random graphs where each variable is a noisy, non-linear function of its parents, with some nodes picked as features and one as the label) produce what real tables have: irrelevant and correlated features, interactions, thresholds, noise, mixed types.
  • When it fails: the posterior is for the prior, not for your data. Tables unlike anything sampled (far more rows than the context, long text, time-ordered data, extreme imbalance) transfer worse.
6What are its main limitations?

Most limits come from doing all the learning inside one forward pass: a capped context, heavy inference and a fixed output size. On top of that it has little built-in explainability, a non-commercial licence and self-reported benchmarks.

  • Context cap: the context holds about 16K rows, so bigger tables are subsampled and the rest of the data goes unused. Trees learn from every row.
  • Rare positives: subsampling hurts most when the signal is rare. A fraud table with millions of rows and a tiny positive rate keeps only a handful of frauds in a sampled context.
  • Inference cost: in the predictor every row attends to every labelled row, so compute grows quadratically with the context, and every prediction re-reads it. That needs a GPU and is slow for real-time scoring, where a tree takes milliseconds on a CPU.
  • Fixed output: at most 10 classes, because the head outputs a fixed set of class logits; the library takes up to 500 features.
  • Explanations: there's no tree structure and no monotonic constraints. SHAP is possible but costs many forward passes, and regulated decisions such as credit need reason codes.
  • Prior mismatch: it's only as good as the synthetic prior's coverage of your data's structure.
  • Licence and evidence: the weights are non-commercial, and the benchmark results are the authors' own.
7How would you evaluate it against XGBoost on a credit dataset?

Compare them the way the model would be used: an out-of-time split, a properly tuned XGBoost, credit metrics plus calibration, confidence intervals, and a learning curve over training-set size, with latency and cost alongside.

  • Out-of-time split: train on older applications and test on later ones. Credit data drifts (the economy, policy, the applicant mix), and a random split lets the model see the future, which flatters both models.
  • A fair baseline: tune XGBoost (depth, learning rate, rounds with early stopping) and add monotonic constraints if production uses them; an untuned tree flatters any challenger. Give TabFM the same training rows, and note when its context forces subsampling.
  • Metrics: AUC and KS (the biggest gap between the score distributions of good and bad borrowers) for how well each ranks good from bad; calibration, because predicted default probabilities feed pricing and expected loss; and the bad rate at a fixed approval rate, the number the business acts on.
  • Is the gap real: bootstrap the test set for a confidence interval on the difference, since small AUC gaps are often noise.
  • Learning curves: repeat at several training-set sizes. TabFM's pretrained prior should help most when data is small; as data grows, trees catch up, because they learn from all of it while TabFM stays capped by its context.
  • Operations: latency and cost per prediction, reason codes for declined applicants, and the licence.

07Cheat sheet

Objective (prior-data fitting)

\[ \begin{aligned} &\min_\theta\ \mathbb{E}_{D \sim p(D)}\big[-\log q_\theta(y_{\text{test}} \mid x_{\text{test}}, D_{\text{train}})\big] \\ \Rightarrow\quad q_\theta(y \mid x, D_{\text{train}}) &\approx p(y \mid x, D_{\text{train}}) \end{aligned} \]

Pipeline

\[ \text{cells} \to \text{tokens} \to (\text{column attn} \to \text{row attn}) \times 2 \to \text{row vectors} \to \text{predictor (attend to labelled rows)} \to \hat y \]
